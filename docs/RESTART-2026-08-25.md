## 4. THE RULINGS THAT GOVERN EVERYTHING ELSE

Locked in step 3 and not to be re-litigated:

1. ⚠️ **APPROVING A REQUEST *IS* CREATING THE ORDER.** A submission is a request to purchase.
   **No order exists before approval.** Booking is a separate step after it. **Payment gates
   FULFILMENT, not booking.** The client never sees the word *approved* — they see *"your order has
   been processed"* and a payment request.
2. **There is no "decline".** A request is **changed** or **cancelled**.
3. ⚠️ **EVERY RECORD IS A PAGE.** Modals are for surfacing information quickly — never
   information-dense, never operationally intensive. **Each record type gets its own page view; the
   layout structure is shared.** Uniformity is the frame, personalisation is the content.
4. ⚠️ **A LEAD IS NOT A RECORD — IT IS AN INBOX ITEM.** No Leads tab. A dashboard notification opens
   the modal with the submission and its handling buttons. **Four exits:** make them a client ·
   marketable lead → marketing zone · cancel → the dungeon · **hard delete with an optional block.**
5. **The submission survives promotion** onto an **Account History** surface, which **replaces the
   Activity Log as a page**; the activity log becomes a link in its top-right.
6. ⚠️ **ONE RESOURCE, TWO VIEWS.** The client edits their fields on their own surfaces; staff see
   **the same record**. Not a copy, not a sync. **A client record page is never shared.**
7. **Timezone is `America/Los_Angeles`** — stored as tenant config, IANA name, never a fixed offset.
8. **Reminders: hourly cron, round the send DOWN.** At hour H, send for bookings starting in
   `[H+1, H+2)`. **Clients get one email** per send.
9. **`med_schedule` generates NOTHING** — the barn does not sell medication as a service. **Do not
   build a task generator from it.**
10. **"Visitor" replaces "guest"** everywhere.
