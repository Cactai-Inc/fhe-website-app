## ⚠️ THE LATENT BUG IS REAL, AND WIDER THAN THE REPORT SAYS

The report flags `fill_party_fields_from_contacts` and `capture_horse_record_info` as ending on the
unsafe re-merge, fixed at their **TypeScript** callers. **Both still call it in the database** —
verified — and `fill_party_fields_from_contacts` is invoked by **ten** other database functions.

**Most of those are safe**, because they re-merge correctly afterwards inside the same transaction.
⚠️ **One is not.**

### `regenerate_contract_document` — the function the contract page calls every time a contract opens

```
PERFORM fill_party_fields_from_contacts(...)   ← blanks a clause document to 23 chars
v_body := remerge_contract_from_clauses(...)
IF v_body IS NULL THEN RETURN …                ← flat template: SAFE, the fill was correct
… replay signatures …
IF v_drifted THEN RETURN …                     ← ⚠️ RETURNS WITHOUT RESTORING THE BODY
UPDATE documents SET merged_body = v_body      ← the repair, never reached on that path
```

**The drift guard protects the value it RETURNS and destroys the value it STORES.**

**It fires when all three are true:** the document is **executed** · the template is
**clause-composed** · the template **version has drifted** since signing.

### Is it armed right now? **No — and it arms itself on the first executed lease.**
The only live contract, `DOC-GCQ4RBNQUN`, is `editable`, so the drift branch is never evaluated and
its 25,739-character body is intact. ⚠️ **But template versions are already at v3 and the templates
are owner-editable.** **The first time an executed lease's template is touched, opening that contract
silently replaces its text with 23 characters.** An executed contract is evidence; this destroys it.

# ⚠️ SETTLEMENT — 2026-08-25, after the build thread disputed the drift finding

**THE BUILD THREAD IS RIGHT. THE FINDING ABOVE IS WITHDRAWN.** Commit `ddc144ba`, *"Close the
23-character wipe at its source (the drift report was wrong)"*, disputes it; verified independently
against production rather than taken on its word.

**Why the finding was wrong — two conditions that cannot both hold:**

| Verified on the live database | |
|---|---|
| `remerge_contract_from_fields` ends its write with `AND workflow_state <> 'executed'` | ✅ confirmed in `pg_get_functiondef` |
| the drift guard evaluates **only** inside `IF coalesce(v_doc.workflow_state,'') = 'executed'` | ✅ `regenerate_contract_document`, the `v_drifted` assignment |

So on an **executed** document the blanking write is filtered out and there is nothing to restore;
on a **non-executed** document `v_drifted` is never true and the function reaches
`remerge_contract_from_clauses` and returns the recomposed body. **The destructive path the report
described requires executed AND not-executed at the same time.**

**Where the error came from:** the report read `remerge_contract_from_fields` returning `23` and
took the RETURN value for the STORED value. The build thread armed all three stated conditions on
the live lease and measured both: returned 23, **stored 25739**.

**The real hazard it found instead is genuine and is the better fix.** Two functions ENDED on a
composer that reads `contract_templates.body`, which holds 23 characters for every clause-composed
template. Nothing was ever lost — but only because all nine database callers happen to recompose
immediately afterwards. **That is a property of nine call sites, not of the function.** The one
reachable window was `capture_horse_record_info` via the app, across two transactions.

⚠️ **The lesson is the same one this pass keeps re-learning:** I named the destructive path from
reading the branch structure and did not check the guard on the write underneath it. **A claim about
what a function DESTROYS has to be measured on the stored value, not reasoned from control flow.**

# ⚠️ THE FAIL-OPEN RISK IS DISPROVEN — `contract_intake_requirements`

The open worry was that `"complete": true` alongside `"my_roles": []` means *"nothing was checked"*
reading as *"nothing is missing"*, letting someone through to the contract without being asked.

**It cannot happen to a party.** Both the authorisation check and the role lookup read the **same
predicate** — `document_parties.contact_id = current_contact_id()`:

- `caller_is_document_party` → `EXISTS (… dp.contact_id = current_contact_id())`
- `caller_party_roles` → `SELECT dp.party_role … dp.contact_id = current_contact_id()`

A non-staff caller who passes the authorisation necessarily has a non-empty role set, so the
person-loop always runs. **The empty-roles result is reachable only by STAFF** — and a staff member
reading someone else's contract genuinely has nothing of their own to give it, which the function's
own comment says is deliberate. `complete: true` for staff is correct, not a hole.
