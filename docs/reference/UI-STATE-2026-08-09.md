# 1 — THE HEADER

`src/components/app/AppHeader.tsx` + `src/components/app/app-header.css` (242 lines).

The **login/public page header, adopted into the app** (ONEHEADER, 2026-08-08). Flat, opaque.
No glass, no blur. It **does not minify on scroll** — the height is fixed per breakpoint,
deliberately, so `--cs-hdr-h` is provably accurate in every state.

**`--cs-hdr-h` IS the header height, not a description of it.** The header takes its height
*from* the variable. Both rails and the contract subheader offset themselves from it. Change
it in one place and everything tracks; hardcode a number anywhere and they silently desync.

| condition | `--cs-hdr-h` |
|---|---|
| default | **76px** |
| `max-width: 600px` | 68px |
| `max-width: 400px` | 64px |
| `max-height: 500px` + landscape + coarse pointer | 56px |

That last block is **a phone in landscape** — ~850px wide but ~390px tall, which the width
queries would otherwise treat as a small tablet and give a portrait-sized header eating a
fifth of the display. It is keyed on height *and* pointer so it can never catch a real tablet
or a narrow desktop window. Inherited from the previous header, which learned it the hard way.
**Do not "simplify" it into a width query.**

Horizontal gutters track `container-site` so the header marks align with page content:
32px at ≥640px, 48px at ≥1024px, each plus `env(safe-area-inset-*)`.

**Known and deliberately unfixed:** superadmin chrome is `h-14` (56px) while the rails read
`--cs-hdr-h` and stick at 76px — a 20px gap. Superadmin chrome is explicitly untouched. This
predates the current header (it was 80 vs 56 before). One inline style on the shared wrapper
fixes it if it is ever wanted.

## The nav is NEAR-WHITE with green ink. It is not green — and it is not cream either.

**`cream-25` is a misleading token name. It renders `#fdfcfa`, which is NEAR-WHITE.** Owner,
2026-08-10: *"the nav on desktop is near white not cream."* Three surfaces are easy to confuse
because two of them really are cream:

| surface | value | what it is |
|---|---|---|
| desktop nav panel | `#fdfcfa` (`cream-25`) | **near-white** |
| page | `#faf8f4` (`cream` / `cream-50`) | cream |
| header | `#f5f0e8` (`cream-100`) | a warmer cream |

**Say "near-white" for the nav.** Calling it cream sends the next person to `cream` or
`cream-100` — a different surface, and any alpha compensation solved against it is wrong.

This reversed an earlier "solid brand green with cream labels" direction, and **the reversal
is not recorded in `OPEN-CHANGE-REQUESTS-2026-08-08.md`** — which still shows the old
instruction under A14.

```
NAV_PANEL      = 'bg-cream-25'                              // #fdfcfa, near-white
NAV_ROW_IDLE   = 'text-green-800'  + hover 'bg-navfill/64'
NAV_ROW_ACTIVE = 'bg-navfill/80 text-cream-25 font-medium'
NAV_ICON_IDLE  = 'text-green-800/70'
```

Near-white panel, green text, green fill only on the selected row (80%) and hover (64%).
`cream-25` is lighter than both the page (`#faf8f4`) and the header (`#f5f0e8`), so the nav
reads as a **raised** surface rather than a heavy slab. Brand green ink clears 13.4:1 on it.

Hover is gated on `[@media(hover:hover)]` — **capability, not width.** A narrow desktop window
has a cursor and expects hover; a phone does not. Do not convert this to a width query.

**The mobile drawer tab is GONE** (ONEHEADER §3, owner ruling 2026-08-08). The header's avatar
button is the only way into the nav on a phone — one control for one job, rather than a tab
bolted to the side of the viewport.

# 3 — COLOUR, AND THE TWO TOKENS THAT ARE NOT COLOURS

`tailwind.config.js`. Brand green `green-800 #143321` · brand gold `gold-600 #ba9935` · page
cream `#faf8f4` · nav panel `cream-25 #fdfcfa`.

## `navfill` and `glass.nav` are INPUTS TO AN ALPHA BLEND, pre-shifted to cancel a hue rotation

Nobody ever sees these values. The owner worked the maths out and was right: **a translucent
green over the warm cream page (hue 37°) composites 72° toward yellow.** `green-800/20` over
cream renders `#c8cac0` — hue 73°, saturation 9%. A grey-green.

So the declared base is rotated the other way and the **rendered** colour lands on brand hue:

| token | over | at | renders | hue | contrast |
|---|---|---|---|---|---|
| `navfill: #0d341e` | near-white panel | /85 | `#31523f` | 145.5° | 8.50:1 |
| `navfill: #0d341e` | near-white panel | /65 | `#617a6b` | 144.0° | 4.55:1 |
| `glass.nav: #09975e` | cream | /30 | `#aed5bf` | 145° | — |

**If the backdrop changes, both tokens are invalid and must be recomputed.** The compensation
is specific to what sits behind them. Worked examples live in `docs/reference/`.

**Established by arithmetic, not taste — do not re-attempt:** a green glass panel over a
near-white page **cannot read as green below roughly 90% alpha.** Back-solving for it requires
negative channel values at 0.20 / 0.60 / 0.80.

`opacity: { 64: '0.64' }` is declared in the config **specifically** so the owner's exact
80/64 pair is expressible. 64 is not in Tailwind's default scale — see T1.

**Type:** `display` and `serif` both resolve to Libre Caslon Text (owner decision, replacing
Cormorant Garamond, which lost the emboss). **It ships 400/700 only — there is no 500.**
Big Caslon is a macOS progressive enhancement only.

# 4 — PAGE SCALING, AND THE "EMPTY PAGE" PROBLEM

`src/index.css`. Root font-size steps up on large displays. Tailwind sizes are rem-based, so
type, spacing **and every `max-w-*` cap** scale together:

```
>= 1400px  ->  18px      laptops, 13-16"
>= 1800px  ->  19px
>= 2400px  ->  20px
```

The 1400px step was moved down from a higher threshold because **a 15" laptop missed the
scale-up by 88px** (`280120e`).

Content columns are centred (`2cc9742`) — part of the earlier emptiness was an alignment bug,
and that part is fixed.

**Open and unsolved:** narrow-capped pages still look empty on a 15" laptop. A `max-w-3xl`
page fills only ~77% of the space beside the rail. **The owner's read is that this is
per-page caps, not the scaling ladder. Do not re-tune the ladder to fix it.**

# 6 — TRAPS. Each one has already cost this project time.

## T1 — An arbitrary Tailwind value can silently emit NOTHING

Typecheck passes. Lint passes. Build passes. The rule is simply absent from the output.

- `bg-cream-100/[0.92]` produced **no rule at all**
- `bg-navfill/64` produced **nothing** — 64 is not in Tailwind's default opacity scale, and
  the hover state silently had no fill

**Any new arbitrary value or non-standard alpha must be grepped out of `dist/assets/*.css`
after a build.** A colour change is not done until that grep returns the rule body.

## T2 — Minified CSS REWRITES what you are grepping for. Two ways.

**a. It keeps the space after the colon.**

`min-width: 1400px` compiles **with** a space. Grepping `min-width:1400px` returns nothing and
looks exactly like a failed deploy. Three consecutive wrong "not deployed" calls came from
this and from comparing bundle filenames on a code-split build — pages are lazy chunks, so
grepping the main entry bundle for a page's code finds nothing whether it shipped or not.

**b. It converts `rgba()` to 8-digit hex. ADDED 2026-08-10 after a near-miss.**

```
authored :  box-shadow: 2px 0 4px rgba(16, 28, 22, .08), 6px 0 18px rgba(16, 28, 22, .10)
shipped  :  box-shadow:2px 0 4px #101c1614,6px 0 18px #101c161a
```

**Grepping the authored `rgba(...)` form returns ZERO.** The orchestrator nearly called a
correctly-shipped rail shadow a silent no-emit on exactly this. Same for white overlays:
`rgba(255,255,255,.14)` ships as `#ffffff24`, and a zero-alpha white ships as `#fff0`.

**How to check a colour actually shipped:** grep the *property* and read what follows —
`grep -oE "box-shadow:[^;}]{0,90}"` — rather than grepping the value you wrote. Or convert
first: alpha `.08` -> `14`, `.10` -> `1a`, `.14` -> `24`, `.15` -> `26`, `.40` -> `66`.

## T3 — Root-level CSS is a different risk class

Nothing lands on `html` or `body` without a browser check. An `overflow-x: clip` on `html`
broke scroll anchoring and **made contract authoring unusable**. Typecheck, lint and build all
passed. Reverted at `259d0e9`.
