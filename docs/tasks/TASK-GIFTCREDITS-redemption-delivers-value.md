# TASK GIFTCREDITS — make a redeemed gift actually deliver something

A recipient can complete the entire gift flow and land in the app **with nothing to book
against**. Four defects, all verified against production 2026-08-07 by the orchestrator.

---

## What already works — do not rebuild it

| step | state |
|---|---|
| Recipient opens the emailed link and sees the gift **without an account** — `open_gift(p_code)`, code-as-credential | ✓ built |
| Claim → `/register?redeem=<code>` when there is no session; the code survives registration | ✓ built |
| After registering, `redeem_gift` marks the gift redeemed and provisions an account | ✓ built |
| Documents assigned; the signing wall gates service features | ✓ built |
| Community access (account-gated, D8) | ✓ built |

The redemption path is real. **The value delivery is missing.**

---

## D1 — redemption creates no credits, no purchase, nothing bookable

`redeem_gift` marks the gift redeemed and provisions the account. It creates **no
`purchases` row, no `purchase_items`, no `fulfillment_units`, and no `lesson_credits`.**

Verified three ways:

- `lesson_credits` has **no gift column**;
- **zero** columns referencing gift across `purchases`, `purchase_items`, `lesson_credits`,
  `fulfillment_units`;
- **no function anywhere** reads a gift and writes credits or a purchase.

So the recipient reaches `/app` as a member and **cannot book the thing they were given.**
The owner's intended flow — *"at the end of which they should see the schedule to request a
booking against the credits given with the gift"* — has no credits behind it.

The data needed is already on the gift: `gifts.item_type` and `gifts.item_label`.

**Build it on the existing spine** (`CLAUDE.md`): `purchases` + `purchase_items` +
`fulfillment_units` generated by `config_kind`, credits consumed by bookings. **Do not
invent a parallel gift-credit mechanism.** A redeemed gift should look like any other
purchase to everything downstream — that is what makes booking, fulfillment and status all
work without special cases.

## D2 — the redeemer is marked CUSTOMER; they are a CLIENT

`redeem_gift` calls `_ensure_client_account(..., 'CUSTOMER')` for the **redeemer**. Wrong,
per the owner's taxonomy (2026-08-07):

> **CLIENT** receives **services — an experience with us.** A riding lesson, even purchased
> once, is a service, so that person is a client.
> **CUSTOMER** bought **a physical thing** and receives no experience.

So:

| party | marker | why |
|---|---|---|
| gift **purchaser** | **CUSTOMER** | bought something; receives no experience |
| gift **recipient**, redeeming a service | **CLIENT** | receives the experience |

Consistent with **D8** ("CUSTOMER = commercial marker for any purchaser incl. gift buyers").
The purchaser side is right in principle; the redeemer side is inverted.

**Edge case to resolve, do not guess:** if the gift is a physical item rather than a
service, the recipient receives a thing and no experience — but they did not buy it either.
The taxonomy does not obviously cover that. **Ask the owner.** Drive the marker from
`gifts.item_type` rather than hardcoding, so the answer is configurable.

## D3 — provisioning failure is swallowed; the gift is consumed anyway

```sql
EXCEPTION WHEN others THEN NULL;  -- never block redemption on provisioning
```

A gift can be marked **redeemed** while account provisioning silently failed. The recipient's
gift is consumed, they have no account, and **nothing is recorded anywhere.** With low
transaction volume the only detection is the recipient complaining.

**The owner has ruled this must be FIXED, not merely logged.**

The intent behind the swallow — don't strand a redemption on a provisioning hiccup — is
sound, so do not simply delete the handler and let redemption fail. Required behaviour:

1. **The gift must not be consumed if the recipient cannot be set up.** Either the whole
   redemption is atomic, or the gift returns to a redeemable state.
2. **The failure must be recorded** — the error, the gift, the user — somewhere staff can
   see it, not `NULL`.
3. **The caller must learn about it.** `redeem_gift` returns a status string
   (`'redeemed'`, `'not_found'`, `'expired'`, …); add a distinct failure status and surface
   it in the UI. It must never report `'redeemed'` when the recipient was not provisioned.

## D4 — nothing creates a gift at all

**There is no gift creation path in the system.**

- No function inserts into `gifts` (scanned `pg_proc.prosrc`).
- No client or API code inserts into `gifts`.
- `gifts` has **0 rows**.
- `requestGift()` in `src/lib/gifts.ts` inserts into **`requests`** with the free-text note
  `"GIFT for <name>"`. It is an **inquiry form, not a transaction.**

So the whole redemption half — `open_gift`, `redeem_gift`, `gift_transfer`,
`gift_claim_link`, `gift_mark_sent`, `gift_reschedule` — operates on rows nothing produces.

**Scope decision for the owner:** is a gift purchase meant to be
(a) self-serve and transactional, creating the `gifts` row directly, or
(b) an inquiry that staff convert into a gift by hand?

Today's code implies (b) but no staff conversion surface exists either. **Ask before
building** — this determines whether D1's purchase/credit creation happens at redemption or
at purchase.

## Verification

1. A redeemed gift produces a `purchases` row with `purchase_items` and the
   `fulfillment_units` its `config_kind` implies — **on the standard spine**, indistinguishable
   downstream from a normal purchase.
2. The recipient can reach the schedule and **book against the credit**, and the booking
   consumes it.
3. The redeemer's account carries the **CLIENT** marker; a gift purchaser carries
   **CUSTOMER**. Prove both with the actual row values.
4. Force a provisioning failure and prove: the gift is **not** left consumed, the failure is
   recorded, and the caller does **not** receive `'redeemed'`.
5. Redemption still completes end to end from the public `/redeem` route for a recipient
   with no prior account.
6. Row counts and existing gift-flow behaviour otherwise unchanged.
