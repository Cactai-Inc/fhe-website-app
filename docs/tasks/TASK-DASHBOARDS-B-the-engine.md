## 5. THE TRAPS (cite in your report which you hit)
- Fresh functions inherit `anon` EXECUTE via default privileges; `REVOKE FROM PUBLIC` is not enough; DROP+CREATE resets the ACL (CLAUDE.md; TASK-BOOKS1/ORIGIN). Every function here ends with the explicit `REVOKE … FROM PUBLIC, anon` and your report pastes `proacl` for all eight.
- Per-account config lands on the ACCOUNT, not the tenant (CR-112 #11): the two-RPC split is the guard; VRFY will call `set_dashboard_provision` as `hello@` on production and prove the row's `user_id`.
- `UNIQUE … NULLS NOT DISTINCT` needs Postgres 15+ — production is Supabase (measure `SELECT version()`); if <15, use a unique index on `(org_id, coalesce(user_id, '00000000-…'), dashboard_key)`.
- Subtractive changes mid-walk (TASK-NOSTRIP): the CHECK drop and the seed are ONE transaction; `dashboard_focus` values are never rewritten.
- Renaming a stored status/value breaks surfaces (LIFECYCLE: nine): `'trainer'`/`'business'` keys never change.
- `CREATE OR REPLACE` with a new defaulted parameter overloads — drop the old signature (any `set_dashboard_focus` / `my_dashboards` signature change).
- Supabase errors are not `Error` instances (TASK-ERRSWEEP) — `useAsync.ts`.
- A component defined inside a component eats keystrokes — hoist.
- RLS is the real "can't reach" bug (TASK-AUTHORITY): the test that a `USER`-role account gets 0 rows from `dashboard_provisions` and cannot call `set_dashboard_default` is in §9.
- `add_lookup_value`'s allowlist (repo memory 2026-08-27): widen by adding, prove by inserting.
- TS-clean ≠ DB-clean (repo memory): run `npm run test:db` with a new `test/db/dashboard_engine.test.ts` on the PGlite harness (`test/db/harness.ts`, `createTestDb`) — the migration must apply on a fresh DB and the fixture `test/db/fixtures/schema_snapshot.sql` may need regenerating (say so).
